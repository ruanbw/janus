# IP 情报按能力抽象,静态 geo 数据做本地兜底

地理字段的注入通道已经存在(`rules.WithGeo` / `rules.Geo`),但全仓没有调用方,`country`/`asn` 恒空,依赖它们的规则条件恒不命中。接入数据源时,接口按**能力**定义而非按供应商定义:`Lookup(ip) → {country, asn, isDatacenter}`;静态 geo 数据(mmdb)与第三方 IP 情报 API 各实现一份,mmdb 同时充当本地兜底;数据源的选择是**平台级**配置,不是租户级;取不到值一律按空值处理,恒不命中。

## 背景与权衡

**接口按能力切,不按供应商切**:`Lookup` 的返回只有规则引擎和访问明细真正关心的三个字段,不暴露供应商自己的响应体。否决「按供应商抽象」(定义 `IPQualityScore` / `IPApi` 之类的供应商接口):那样每个新供应商都要新增一个类型并改所有调用点,而规则侧要的从来不是「这个供应商返回了什么」,只是「这个 IP 属于哪个国家、哪个 ASN、是不是机房」。供应商特有的字段(货币、时区、风险分)留在各自实现内部,不在接口上流通。

**mmdb 做本地兜底,而不是二选一**:求值发生在跳转的同步路径上(`redirect.go` 在 `snap.Evaluate` 之前构造访客画像,而 `country` 是可判定字段),所以数据源不可用不是"规则条件少命中几条"的问题,是**每次跳转多一次外部往返延迟加一个外部故障点**。让远程实现失败时回落到本地 mmdb,代价只是"多一个要维护的 mmdb 文件",收益是把第三方抖动从"线上短链变慢或 500"降级成"降级到静态库的精度"。反过来,只装 mmdb 不要兜底是不可接受的:静态库不更新就会静默过期。

**取不到值按空值处理,恒不命中**:沿用 `internal/rules/eval.go` 里已写明的不变式——取不到数据的字段绝不"默认放行"或"默认拦截"。否决「取不到时跳过该条件」:那等于把情报服务故障翻译成"规则悄悄变松",风控规则会在服务故障期间全部失效;也否决「取不到时按未知国家拦截」:那是把服务故障翻译成"全站不可用"。恒不命中的方向是安全的——顶多是一批依赖地理的规则不生效,访问照常走。

**数据源选择放平台级,不是租户级**:一次加载、进程内全租户共享。否决租户级选择:按 IP 的解析结果缓存是全局的,而配额和限流是按 API key 计的,租户级选择会让同一份 mmdb 在进程里按租户切分、或让第三方配额在租户之间互相挤兑,复杂度远超收益。`internal/config` 目前全是环境变量驱动的,起步也用它,不为此新建配置表;真要做成 UI 选择,载体应是平台级设置而非挂在 `tenants` 上。

## 后果

- 任何实现都必须带进程内按 IP 的缓存,并且**必须缓存负结果**。不缓存负结果等于把每次查不到的 IP 都变成一次远程调用,足以打爆第三方配额。
- 求值期仍是纯内存的:lookup 发生在构造 `Fact` 之前,不在 `Evaluate` 里,`Evaluate` 内部零 IO 这条不变式不能破。
- 远程实现必须设定超时上限并在超时/错误时回落,超时预算的具体数值在实现时定,但"必须有上限"是硬要求。
- `migrations/0008_visit_action_geo.sql` 的 `country` / `is_datacenter` / `asn` 三列已就位,实现只需在 Go 侧解析填充,不改表结构、不动前端——这是 ADR 0007 写下的计划,本条没有改变它。
- `is_datacenter` 目前只落库供访问明细展示:规则侧只有 `FieldCountry` / `FieldASN`,`WithGeo` 也只接 country/asn。要支持"拦截机房 IP"得先给规则加可判定字段,那是另一条决策。
- 用户可见的"地理数据源"选择项在平台级配置落地前不存在;界面上"地理数据源待接入"的占位提示可以在实现时换成实际数据源名。
