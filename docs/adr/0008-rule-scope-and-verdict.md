# 规则与短链的关联由规则侧声明;访问裁决取首条命中

后台的「规则引擎」此前是纯前端原型:规则挂在租户上,没有任何东西把它和具体短链连起来,「仅对活动短链生效」这类需求无法表达。本次把规则变成可作用在具体短链上的处置规则,并让访问链路执行它其中两个决策不显然,单独记录。

## 背景与权衡

**关联由规则侧声明生效范围,而不是短链侧持有规则列表**:规则带一个作用域,取值为全局或指定短链;指定短链时,适用关系落在一张关联表里。全局规则在关联表里没有任何行。否决反向方案(短链持有自己的规则列表):同一份关联要在两个方向各存一次,必然漂移——两边各写一遍的场景在带 UI 的系统里不是"可能",是迟早;而且全局规则在短链侧根本无法表达,要么冗余落成 N 行,要么每次查询都回查规则的作用域。双向都做更糟:字段重复、写路径双份,没有收益。规则侧是唯一写入口,短链表单里勾选一条指定短链作用域的规则,本质就是改写该规则与本短链的关联,两边读的是同一份数据。代价:短链列表要显示规则元数据必须额外回查一次关联表(且必须批量,否则 N+1),但这是一次可缓存的读,与双写会写歪不是一个量级的风险。

**首条命中即裁决,不做多规则叠加**:规则按优先级升序求值,第一条命中的规则决定这次访问的处置,后面的规则不再参与。考虑过命中多条时合并动作(取最严),以及允许排在后面的放行规则覆盖前面的拦截。否决:叠加语义下,一条低优先级的放行规则可以静默救回高优先级拦截规则的访问——租户在规则列表里看到「拦截」,线上却放了过去,这类静默失效的排查成本极高,且是否发生完全取决于 priority 有没有认真排。首命中把歧义消灭在排序上:想要多套规则并存,就显式排优先级,而不是依赖叠加的隐式语义。代价是平台不再替租户合并意图,多套规则的先后关系完全由租户自己的 priority 承担。

## 后果

- 短链侧的"适用规则" = 全局规则 ∪ 与本短链关联的指定短链作用域规则;取消勾选只删关联,不会影响全局规则。
- 一条指定短链作用域但零关联的规则永远不命中,后端不拦截这种创建(它是合法状态),但界面必须显式标出「未关联短链 · 不会命中」。漏标就是"以为只影响活动短链、某天却被悄悄打到全租户流量"的入口。
- 裁决是单条的:命中哪条规则与它给出的处置是同一次求值的结果,访问明细里不会出现两条规则各说各话的记录,也不存在"这次访问到底被几条规则看过"的问题。
- 规则排在短链可用性之后:短链自身已停用/已删除/无目标/落地页文件缺失的访问直接失败,明细里没有规则字段。
- 代价:租户需要多套规则并存时必须显式排 `priority`;默认优先级相同的规则之间,谁先谁后是租户的配置责任。
- 规则集合按租户整份缓存在内存,任何规则写入或关联变更都必须失效对应租户的快照——漏失效会让刚保存的规则在下次快照重建前完全不生效,且没有任何报错。
- 若将来要支持多规则叠加,必须另开一条 ADR 明确冲突消解规则;在此之前不要在代码或界面上预留叠加入口。
